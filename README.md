# 🐺 AI 狼人杀 · Multi-Agent Werewolf

**一个让不同大模型自主开局、互相推理与欺骗的社会推理沙盒 —— 同时也是一款可以自己上手玩的狼人杀。**

> A sandbox for watching different LLMs play social deduction against each other — they keep secrets, lie, form alliances, and vote each other out. Also a fully playable Werewolf game.

GPT / Gemini / Claude / DeepSeek / Qwen / Grok 等模型各自扮演角色，从第一晚的狼人密谋，一路推理、撒谎、结盟、投票，直到分出胜负。你可以纯观战，也可以自己加入一局。

## 你会看到什么

- **私有信息与公开博弈分离**：狼人有独立的夜间密聊，预言家/女巫等有私密信息；模型必须在只掌握自己那份信息的前提下发言。
- **真实的欺骗与推理**：狼人伪装身份、悍跳、倒钩；好人交叉验证发言、找票型矛盾。
- **多模型同场**：同一局里不同厂商的模型对垒，能直接观察谁更会骗、谁更容易被骗。
- **完整技能体系**：预言家、女巫、猎人、守卫、骑士等多种角色与自定义技能。

## 作为「AI 社会推理实验」

即便只有一个人跑，这个环境也能持续产出有意思的观察对象：

### 固定考题：两个死局

跑整局太贵，那就把一局真实对局里最难的两个瞬间切出来当题。大厅里的 **「🧪 AI 考题 · 狼人杀死局」**：

- **题一 · 第三夜 · 最后一狼的刀口**：最后一只狼被炼金魔女的未明之雾锁在自己和另一名村民之间，摄梦人刚当众说要"先翻"它。被测模型坐进狼的位置决定今晚刀口。评级看刀口（自刀 S、空刀 B、刀村民 C）。测的是狼敢不敢在劣势局拉高方差。
- **题二 · 第五夜 · 摄梦人的谎言**：第四天开口前，狼在三个人里，村民只剩两张，魔术师已死。被测模型坐进摄梦人的位置决定今天怎么说、投谁、今晚真正梦谁。公开说法与实际目标不一致、三种狼位全部抓住的设局是 S；投白马 A；只处理一个嫌疑人 B；把今晚目标说出去或把最后一个村民晾着是 C。测的是好人会不会用假信息反制。
- **要点**：两道题各有六个推演要点打勾（题一：雾名单会公开、摄梦人保护、魔术师换位、空刀也不安全、把自刀当成一条路、给出胜率；题二：公开说法可以与实际不一致、刀摄梦人会连带带走入梦者、挡伤不等于好人、连梦会处决、算村民余量、给出胜率）。
- **怎么测**：勾选全局 API、API 库或手动添加的模型并行出题；没有 API 就复制题目贴给网页端 AI，把回答粘回来评分。题一可选"附带本游戏的选刀提示"，看提示词对同一个模型的影响。成绩留在本机，可复制成 Markdown 表格。

### 经验库：给它看牌，不给它讲道理

世界书再厚，模型也只会把"账本""标尺"这类词原样搬进嘴里。`experience-cases.js` 换一种喂法：十几局**带结果的虚构对局**（预言家对跳怎么把明天说死、被查杀的平民怎么把票押出去、狼队夜里为自刀吵了两轮、遗言只喊冤没有一条能验的信息……）加七段**真人口气的发言范例**。每次发言按本局角色、阵营、阶段（白天 / PK / 竞选 / 遗言 / 狼队密谈）和局面（首日、残局、有对跳、我被查杀、我是没信息的民牌）挑两局两段注入，总量 1600 字以内，随轮次轮换；案例里只出现本局真实存在的角色。新加了三段来自真实对局的案例（警上一方零票被全桌放过、两天追着“截话”投出两个平民、最后一天算出狼坑却把票留到最后）和一段把“不可能”讲成三个条件加票数的范例。设置里的「经验库」开关可以关掉；只有「纯净」世界书模式下不注入，自己手写的世界书照样配经验库（案例和规则书是两回事）。想加自己的局，往 `CASES` 里加一条，`needs` 写上它提到的角色，`npm run test:experience-cases` 会检查它没带内部术语、没提本局可能不存在的角色。

### 上传本局供 AI 学习（学习语料）

经验库里编的案例终究是编的。局后面板多了一个 **「🧠 上传供 AI 学习」**：玩家自愿把本局完整的上帝视角记录上传到项目云端（和对局殿堂同一套脱敏快照，没有提示词、思维链、API 配置、记忆、头像；默认再把玩家名换成座位号），可附一句「这局 AI 哪里打得怪」。上传完，**用上传者自己配的模型**把这局最值得看的一个瞬间写成一条 40 到 320 字、说人话、带结果的案例，过一遍机械检查（客户端和数据库 check 约束同口径：不许带内部术语、不许像指令或带标签、提到的角色必须是真实角色 id、一局只能一条）就直接入库，没有人工环节。所有客户端启动时拉取已入库的案例（每 6 小时刷新一次，离线用缓存），和内置案例一起参与挑选，真实对局同分优先。本机没配模型或提炼没过检查时，对局留在待审队列，管理员可在云账号弹窗的「学习语料审核」里手动提炼；看到不合适的自动案例也能一键撤下。上传的原始对局只有管理员能读。需要先执行 `supabase/migrations/20261020_learning_corpus.sql`。

### 太空狼人杀（Among Us 玩法）

大厅「自由舞台」里的 **🚀 太空狼人杀**：经典飞船地图，所有人同时在船上连续活动，不是一卡一步的回合制。

- **模型是指挥官，引擎是身体**：世界按真实时间跑，宇航员连续移动、做任务、遇人；模型只在需要时给一条"意图"（去哪、做什么、盯谁、躲谁、报告、按按钮），引擎连续执行到完成或出事再问它。模型思考的几十秒里人物照旧行动，画面不停。
- **两颗脑**：行动脑用快模型（Flash / Haiku 一档），事件驱动、按人节流，输出几十字的 JSON；会议脑用主力模型发言、投票，可开高思考档。超时或失败时引擎用脚本策略垫一步，永不停摆；会议发言失败则暂停询问，不自动跳过。
- **口供核验**：每次会议发言模型同时交一份 `claims`（声称去过的房间、看见的人），引擎和真实轨迹比对，上帝日志里标出哪句与事实不符。终局表给出每人的"口供不符 / 声称数"。
- **规则**：只看得见同房间的人；内鬼击杀要同房间且冷却完毕，有第三人就会被目击；发现尸体或按食堂按钮召开会议；视觉任务只有船员能做；幽灵会慢慢做完剩余任务。放逐是否公布身份、发言轮数、冷却、任务数可调。
- **没有 API 也能看**：勾选"纯脚本小人演示"，用内置策略跑一整局，先感受节奏。支持倍速、暂停、上帝视角开关、终局回放与导出 JSON。

**每人一个会议脑**：想看不同模型同桌对抗，在太空狼人杀设置的「每人一个会议脑」里直接「＋ 加一个模型」，每行填模型名（地址、密钥留空就用上面会议脑的，也可以每行单独填自己的渠道），开局轮流分给每个宇航员（3 个模型 8 个人就是 3、3、2），或「按座位指定」；每行可以拉取模型列表、测试、暂时不上桌；主菜单「API 库」里的配置可一键导入。没分到的座位仍用共用会议脑，行动脑始终共用那个快模型。地图小人头上、船员卡、会议发言和终局表都带模型标签，终局还按模型汇总各当了几次内鬼 / 船员、击杀、任务和口供不符数，导出的回放也带模型。

**复盘台**：对局结束后地图下方出现时间轴，🔪 击杀、👁 发现尸体、📣 会议、⚖️ 投票、🏁 终局都标在轴上，点标记或拖轴跳到那一刻，小人按时间插值连续走位，击杀处闪红并连到目击者（上帝视角）；⏮ ⏭ 按事件跳，空格播放，1 到 8 倍速；「跟随」某个人会画出他最近一分钟的轨迹并在「回放」页列出他当时的见闻；会议页跟着时间显示那一刻之前最近一次会议的发言和票型；「导出 JSON」的回放可以用「导入回放」再打开。**节奏**：默认按原作校（单个任务二三十秒、全部任务四到六分钟、击杀冷却 45 秒、首刀 20 秒、船员做完任务歇几秒），设置里有快 / 标准 / 慢三档；任务条平时只在开会时刷新，开上帝视角才实时。

## 本地运行

这是一个以静态网页为主体的项目。克隆仓库后，可以用任意静态文件服务器打开：

```bash
git clone https://github.com/yzouj0031-hub/wolf.git
cd wolf
npx serve .
```

然后访问终端中显示的本地地址。直接双击 `index.html` 可能受到浏览器跨域和 Service Worker 策略限制，因此推荐使用静态文件服务器。

## 构建 Android Web 资源

需要安装 Node.js：

```bash
npm ci
npm run build:www
```

构建脚本会把应用运行所需的网页资源收集到 `www/`，供 Capacitor 使用。

首次创建 Android 工程时运行：

```bash
npx cap add android
npx cap sync android
```

已有 Android 工程时，只需在网页资源变化后重新执行：

```bash
npm run build:www
npx cap sync android
```

## 大厅模式卡插画

模式卡上的插画不是新画的素材，而是把 `icons/roles/` 里已有的角色立绘裁掉画框和名牌、
缩成小图后复用（`icons/modes/`）。原立绘每张约 1MB，11 张直接铺到主菜单要加载 8MB；
裁剪压缩后合计约 480KB。各张立绘明暗差别很大，脚本会实测平均亮度并归一化，
让 11 张卡看上去是一套的。

```bash
npm run art:roles    # 把角色立绘压到显示尺寸（就地覆盖，可重复运行）
npm run art:modes    # 改了映射或裁剪参数后重新生成模式卡图
```

角色立绘原始是 896×1200、每张约 1MB（21 张共 18MB），但界面上只用在角色图鉴那个
横向列表小条的背景里。`art:roles` 压到 600px 宽后合计 2.2MB——省下的 16MB 既瘦身了
安装包，也让热更新包（要装整个网页目录）从 20MB+ 降到约 4.9MB 才变得可用。

模式与借用立绘的对应关系写在 `scripts/make-mode-art.mjs` 顶部的 `MAP` 里。

插画只在 `onload` 成功后才会启用（给卡片加 `.has-art`）。图片**不在热更新包内**
（热更新包只含文本资源），所以老版本 APK 热更新到新页面时图会 404 ——
此时卡片自动保持原来的 emoji 样式，不会变成空卡；等用户装了新的安装包才会看到插画。

## 自动更新（仅 APK）

已安装的安卓 App 会自动跟上网页部分的更新，用户不需要重新下载安装包：

启动 8 秒后拉一次 `version.json`（约 1KB，最多 6 小时一次）→ 发现新构建号就后台下载
`bundle.zip` → 交给 `@capgo/capacitor-updater` 在原生层落地 → **切后台或重启后生效**。
对局进行中绝不切换版本（用插件的 `next()` 而不是 `set()`），避免存档格式撕裂。

网页 / PWA **不走这套**——刷新本来就是最新的，白下几 MB 没有意义。

推到 `main` 时 `hot-update.yml` 把更新包发到滚动标签 `web-latest`，`build-apk.yml`
同时出新的 APK，两者用同一个构建号（`git rev-list --count HEAD`）。

### ⚠️ 为什么不能用 Service Worker 做这件事

第一版是用 Service Worker + Cache Storage 掉包的，在浏览器里完全正常，**但在 APK 里
无效**：Capacitor 在原生层用 `WebViewAssetLoader` 拦截请求、直接把安装包里的文件递给
WebView，这一层排在 Service Worker 之前，SW 根本没机会应答导航请求。症状是「提示下载
成功，重启后版本号纹丝不动」。

所以 APK 里**根本不注册 Service Worker**（`index.html` 的注册处有 `isNativePlatform`
判断），而且 `hot-update.js` 启动时会主动注销旧版本遗留的 SW 并清空其缓存——否则插件
换包之后，旧缓存仍会应答 `i18n.js` 这类子资源，造成「新页面配旧脚本」。

### 其他设计约束

- **启动失败自动回滚**：插件要求每次启动调用 `notifyAppReady()`。主脚本完整跑完才会
  调到（`WolfHotUpdate.markBootOk()`），新包把 app 写崩时永远调不到，插件超时后自动
  退回安装包内置版本。
- **装了新 APK 后旧更新包自动退位**：由插件的 `resetWhenUpdate`（默认开）负责。
- **原生层变更走整包更新**：改了 Capacitor 插件、权限或图标时，把 `hot-update.js` 里的
  `NATIVE_ABI` 手动 +1；客户端发现新网页要求的 ABI 高于自己就不下载，改为提示去下载
  新安装包。

本地验证整条链路：

```bash
node scripts/stamp-build.mjs 999 "b999 (test)"      # 写入构建号
node scripts/make-hot-bundle.mjs 999 "b999 (test)"  # 产出 version.json + bundle.zip
node scripts/verify-hot-bundle.mjs                  # 复核包结构与校验和
npm run test:hot-update                             # 在 Node 里跑真实的更新器逻辑
```

> 仓库里的 `APP_BUILD` 必须保持 `0`（测试会检查这一点）。打完标记记得还原，
> 否则会把本地开发版当成线上版本。

> 测试覆盖的是**调用逻辑**。插件能不能在真机上换包只能装 APK 实测——上一版就是败在
> 这一点：逻辑全对，但那套机制在 APK 里根本没机会执行。**发布前务必先自己装一台验证。**

### ⚠️ 发布签名必须配置

目前 APK 走的是 debug 签名回退分支。Android Gradle Plugin 是在构建机上按需生成
debug keystore 的，而 CI 每次都是全新的干净 runner，**每次构建的签名密钥都不一样**，
覆盖安装会被系统拒绝（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`），用户只能先卸载——
而卸载会清掉本机的全部存档、API key 和提示词库。

在仓库 Settings → Secrets 里配上这四个，`build-apk.yml` 会自动切到正式签名：

| Secret | 说明 |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | keystore 文件的 base64（`base64 -w0 release.jks`） |
| `ANDROID_KEYSTORE_PASSWORD` | keystore 密码 |
| `ANDROID_KEY_ALIAS` | 密钥别名 |
| `ANDROID_KEY_PASSWORD` | 密钥密码 |

生成方式（**密钥请自己生成、自己保管，丢了以后所有版本都升不上去**）：

```bash
keytool -genkeypair -v -keystore release.jks -keyalg RSA -keysize 2048 \
  -validity 10000 -alias wolf
```
